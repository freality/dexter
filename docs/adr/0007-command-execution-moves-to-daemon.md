# Command execution moves to the daemon; host privileges mean the daemon's host

`dex run <name>` (map #10, ticket #16 "Thin client") today evaluates a project's registered Commands and runs their host-exec calls as a child of the `dex` CLI process itself (`run.go`'s `hostExec`: "runs argv as a child of the dex process with stdio attached") — on whatever machine invokes the CLI, which is trivially also wherever the project lives, since no daemon exists yet. ADR-0004 already moved all project evaluation (synthesis via `goja`) into the daemon, for every other CLI command; `dex run` predates that decision and still reads `.dex/state.json` directly and executes locally. Once a `--daemon <remote-host>` invocation is possible (ticket #16), that gap becomes a real behavior split: does a Command keep running on the CLI's own machine, or does it move with everything else into the daemon?

Resolved: `dex run` (and bare `dex run` for listing) routes through the daemon's `RunCommand`/`ListCommands` RPC (#13's "Daemon core" already specified this RPC shape), the same as `plan`/`apply`. A Command's host-exec calls therefore run with **the daemon's host privileges**, not the invoking CLI's. For an ephemeral or same-host persistent daemon this is no visible change — same machine either way. For a genuinely remote persistent daemon, it is: a Command triggered from a laptop now executes on the homelab server the daemon runs on, not the laptop. This is also the only way a `dash`/web GUI/MCP-triggered Command makes sense at all — those clients have no "local machine" of their own to run anything on relative to the managed infrastructure; the daemon's host is the only sensible target. `GLOSSARY.md`'s **Command** entry ("runs ... with host privileges") is sharpened to name whose host explicitly, closing what was previously an implicit, single-machine assumption.

A second, smaller consequence: `RunCommand` streams output only (stdout/stderr as `Event`-shaped log lines, the same pattern `Apply` already uses) — no bidirectional stdio streaming, and the daemon's host-exec runs a Command's child process with **stdin closed**, not attached to anything. Three reasons this is the right trade-off rather than an oversight:

- Multi-client ambiguity has no good answer: with `dash`, the web GUI, and MCP all able to trigger `RunCommand`, bidirectional streaming would have to pick one caller as "the" interactive terminal, which doesn't generalize to a Command triggered by, say, an AI assistant.
- A closed stdin degrades gracefully for well-behaved tools: `isatty(stdin)` correctly reports false against a closed descriptor, so anything that already checks for a TTY before prompting (most modern CLIs) silently takes its non-interactive path, unaffected.
- For a tool that blocks on reading stdin regardless, a closed descriptor means `read()` returns EOF immediately instead of hanging the whole RPC indefinitely with no signal back to the caller about why.

This matches Commands' own stated nature in `GLOSSARY.md` — day-two automation (backups, restarts, migrations), not interactive wizards — so the constraint costs nothing a real present use case needs.
