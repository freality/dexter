# dex dash multiplexes Stats/Logs at the daemon, and is a live view, not a persistence guarantee

`dex dash` (map #10, ticket #17) consumes two kinds of daemon subscription: apply events, already fanned out per-subscriber by ADR-0004's design, and the `Stats`/`Logs` RPCs ticket #12 added between the daemon and an adapter. Nothing before this ticket decided what happens between the daemon and *N connected dashboard clients* watching the same resource's telemetry.

Resolved the same way as apply events: the daemon holds at most one upstream `Stats`/`Logs` subscription per resource, open to the adapter, fanned out to every daemon-level subscriber through the same bounded-channel, drop-slow pattern ADR-0004 already established for events. A second `dash` instance, or the web GUI, watching the same resource attaches to the daemon's existing upstream stream rather than opening a second one against the adapter — the adapter does the work of producing telemetry once per resource regardless of how many clients are watching it.

A corrected premise, recorded here because it was wrong in an earlier ticket comment before being caught in review: `dash` does **not** require a persistent daemon. An ephemeral daemon's lifetime is tied to its *spawning CLI process* (ADR-0004), and `dash` is itself a long-running foreground command, not a one-shot — a `dash`-spawned ephemeral daemon lives exactly as long as the `dash` session does, and live streaming works against it the same as a persistent one. `dash` attaches to whatever daemon is already running or gets spawned, via the same detection `plan`/`apply` already use; no special-casing for `dash`.

What an ephemeral daemon genuinely doesn't provide on its own is cross-*session* history — but map #10's Notes already commit to durable event logging for GitOps/cron applies specifically ("log every event durably for `dash`/web GUI replay"), a decision made during charting, not reopened here. `dash` calls a replay RPC on attach to catch up on history from before it connected, on top of the live `WatchEvents` stream it then switches to. The log's own mechanism — storage, retention, scope (every event or only GitOps-triggered ones), and the replay RPC's exact shape — is undesigned and graduates to its own ticket, "Durable event log" (#22), which blocks "GitOps/cron" (#20) since that ticket is what the mechanism was first motivated by.
