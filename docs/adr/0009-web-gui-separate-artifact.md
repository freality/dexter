# The web GUI ships as a separate, optional artifact, not embedded in the dex binary

Map #10's Notes originally fixed this during charting: `packages/web` "built at `dex`'s own release time ... and embedded into the Go binary via `go:embed`," the same pattern `pkg/jsenv/sdk/embed.go` already uses for the SDK bundle. Ticket #18 ("Web GUI") revisited that while scoping the web GUI's design, and reverses it.

The adapter-extraction precedent (Phase 2, `docs/plans/phase-2-extensibility.md` D6–D9: the Docker adapter moved into a standalone binary) doesn't actually transfer cleanly. That decision was driven by two things — keeping `moby/moby`'s dependency footprint out of `cmd/dex`'s module, and letting third parties distribute their own adapters independently of this repo's releases — and neither applies to a static asset bundle: serving it needs nothing beyond `embed` (stdlib), and ROADMAP describes one official web GUI, not a third-party extension point.

What does apply, for a different reason: the web GUI is the most prunable of Phase 3's six ROADMAP items (the map's own charting round flagged it as the likely candidate to cut, overlapping with `dex dash`), in a project that otherwise keeps its core binary deliberately lean (zero-runtime TypeScript authoring, MIT-compatible-only dependencies). Embedding it unconditionally means every CLI-only or `dash`-only user carries an asset bundle they may never open a browser to see, and every web-GUI-only bugfix forces a full `dex` binary release to ship.

Resolved: `packages/web` builds its own static-asset tarball, published as its own GitHub Release, decoupled from `dex`'s own release cadence. It's fetched into `.dex/web/` via the same GitHub-Releases-fetch infrastructure Phase 2 already built for adapters, reused as a shared internal helper rather than literally `dex plugin add` (a static tarball isn't a `go-plugin` binary and needs no handshake) — likely its own small command, `dex web install`. The daemon serves `.dex/web/` from disk via a plain `http.FileServer` when present; absent, the web GUI route simply isn't served, the same shape as an uninstalled adapter's "not installed, run X" error today.

This reopens the exact problem ticket #21 already exists to solve for adapter binaries: a `--daemon <remote-host>` invocation (#16) means the CLI fetching an artifact locally doesn't put it anywhere the daemon can see. #21 is widened to cover both artifact kinds — adapter binaries and the web GUI bundle — rather than solving the identical problem twice.
