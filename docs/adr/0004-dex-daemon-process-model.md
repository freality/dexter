# The CLI is always a daemon client; the daemon's lifetime, not its code, varies

Phase 3 could have given `dex plan`/`dex apply` two implementations: today's in-process `engine.Engine` for the no-daemon case, and a gRPC client for the daemon case, switched by detection. Resolved in grilling (map #10, ticket #13 "Daemon core") to one implementation instead: the CLI is *always* a gRPC client, and "standalone" just means the daemon it talks to is a child process it spawns itself — **ephemeral**, watching its spawning CLI's pid for its entire life (reusing the existing `watchOrphan` pattern from `pkg/plugin/plugin.go`) and exiting the moment that CLI process exits, clean or crashed — versus **persistent** (`dex daemon`, run explicitly or under a supervisor, stays up until stopped). `engine.Engine` becomes daemon-only code; `cmd/dex/internal/cli`'s in-process `newProductionEngine` path goes away entirely. One code path to maintain, and both lifetimes share the same detection and locking mechanics, rather than the file lock meaning something different depending on which path a command took.

An ephemeral daemon has no idle timeout of its own: `watchOrphan` on the spawning CLI's pid is the only governor of its life, not a debounce timer on top of it. That single mechanism has to span the whole command, including the gap between `Plan` returning and the user typing `y` at the confirmation prompt — the CLI process is alive but has no open gRPC stream for that entire gap, so anything keyed off "last stream closed" would kill the daemon mid-confirmation. Tying exit to the spawning process's lifetime instead of to stream activity covers that gap for free. The cost: a daemon never outlives the single command that spawned it, so two independent, sequential invocations each pay their own ephemeral startup — deliberately not optimized for, since overlapping/concurrent invocations (two terminals running at once) already share one running daemon for free through the detection mechanism below, with no timer needed for that case.

Detection and the bind-time socket constraint: a non-blocking `flock` on `.dex/daemon.lock` is the single-instance mutex (winner binds, loser connects, same mechanics for either lifetime); `.dex/daemon.info` holds the connection details, written only after bind succeeds. Both stay inside the project directory — plain file I/O, no length limit. The actual `.sock` file bound by `AF_UNIX` cannot: `sun_path` is capped at 104 bytes on macOS, 108 on Linux, and a project nested a few directories deep routinely exceeds that. The socket itself binds under a short, OS-appropriate runtime directory instead (`$XDG_RUNTIME_DIR` on Linux, `$TMPDIR` as the portable fallback), named from a short hash of the project's absolute path so it stays both unique and comfortably under the limit regardless of nesting; `daemon.info` records that resolved path for clients to read.

Two further consequences of "always remote" that a future reader would otherwise have to rediscover by reading the diff:

- **Env propagation.** `root.go`'s `mergeProcessEnv` today overlays the CLI's own process env on `.env`. An ephemeral daemon gets that for free via normal process inheritance; a persistent daemon — especially a remote one, explicitly in scope per the map's LAN-reach decision — only has its own env. Rather than special-case the two, the `Plan` RPC carries the caller's env explicitly, merged server-side identically to today, uniformly for both lifetimes. This means a remote persistent daemon receives the calling shell's full environment over the LAN on every plan. Accepted deliberately: the map's Notes already scope this effort to a trusted LAN (internet exposure is out of scope), and TCP connections require the shared token regardless.
- **Ctrl-C.** Today it cancels `ctx` directly, aborting the apply. Over gRPC it only cancels the caller's stream. An ephemeral daemon treats that as "my one owning client disconnected, cancel the apply" (today's behavior, unchanged). A persistent daemon treats it as "that client stopped watching" only — the apply keeps running, since other clients may be watching the same apply through `WatchEvents`. Actually cancelling a persistent-daemon apply needs a future explicit action (e.g. `dex apply --cancel`), not designed here.
